Contexto // fundamentos

AI coding em 60 segundos

Um assistente que escreve código junto com você — lê o repo, entende o pedido, edita arquivos, roda testes e abre PRs.

Claude Code e Codex (OpenAI) são os dois pesos-pesados que rodam no terminal. Também existem Cursor, Windsurf, Gemini CLI.

Em PT
Repo é a pasta com todo o código de um projeto, versionada (cada alteração fica registrada). Terminal é a tela preta de comandos onde devs vivem — é onde esses agentes rodam.
# você pede em linguagem natural
> "adiciona um endpoint /health
    no server.py e um teste"

# o agente lê o código, edita,
# roda o teste, commita
✓ server.py            +12
✓ tests/test_health.py +18
✓ pytest passou
✓ git commit -m "..."

Dicionário rápido

9 termos que vão aparecer — guarde essa página

repo
Pasta com todo o código de um projeto, versionada. Toda alteração fica registrada.
commit
Um "save" do código com mensagem explicando o que mudou. O bloco atômico da história.
PR (pull request)
Proposta: "quero juntar esses commits no código principal". Passa por revisão antes de entrar.
endpoint
Um "botão" da API — URL que o sistema responde. Ex: GET /health → "estou no ar".
teste / pytest
Código que testa outro código automaticamente. Roda em segundos e acusa se algo quebrou.
token
Unidade de texto que o modelo "lê" (~1 palavra = 1-2 tokens). O contexto é medido em tokens.
XML
Formato de texto com etiquetas (<task>...</task>). Modelos de AI parseiam com quase zero erro.
CLI / terminal
Tela preta de comandos. Claude Code e Codex vivem ali — não é um chat web.
agente de AI coding
Claude Code, Codex, Gemini CLI — ferramentas diferentes, mesmo papel: ler o repo, editar, rodar, commitar.

O modo padrão

Vibecoding: descreve, gera, reza

"faz um sistema de login com JWT, OAuth Google e reset de senha" PROMPT TÍPICO

Funciona bem em protótipo, landing page, script descartável. Quebra feio em código sério — e ninguém sabe onde quebrou.

Em PT
Alucinar import = o modelo inventa uma função que não existe na biblioteca real. Refactor = reorganizar o código sem mudar o que ele faz.
  • FAIL 01Alucina imports que não existem na versão da biblioteca
  • FAIL 02Esquece contexto no meio de um refactor grande
  • FAIL 03Edita o arquivo errado, ou escreve sobre trabalho em andamento
  • FAIL 04PR monstro de 40 arquivos, nenhum commit atômico
  • FAIL 05Declara "pronto" sem rodar o código
GSD · GUILD AI05 / 23
O gargalo invisível

Context rot — sessão longa vira código ruim

O modelo tem janela de contexto finita (ex: 200k tokens).

Cada arquivo lido, cada ferramenta, cada erro de teste ocupa espaço. Quando enche, a qualidade despenca: o modelo "esquece" arquivos que acabou de ler, reinventa código existente, entra em loops sutis.

Em PT
Pensa na memória de trabalho do modelo como uma mesa. 200k tokens = mesa de tamanho X. Quanto mais papel você empilha, mais coisa cai da mesa — sem você perceber.

GSD · GUILD AI06 / 23
Os 3 pecados

Por que AI coding falha em produção

Não é "o modelo é ruim". É que o workflow está quebrado.

01

Sem plano

Pula direto pra "gera o código". Sem critério de sucesso, sem quebra em etapas, sem rastro.

02

Contexto saturado

Tudo numa sessão só. Quando chega na task 5, o modelo já esqueceu a task 1.

03

Sem verificação

"Pronto!" sem rodar código, sem teste, sem UAT. PR de 2000 linhas, nada atômico.

Em PT
UAT (User Acceptance Testing) = teste de aceite — verificar se o que foi entregue atende ao que foi pedido, na prática.
GSD · GUILD AI07 / 23
A ponte // conceito

Spec-Driven Development — por que isso importa

Ideia central: escreva o contrato antes do código. Depois cada passo se deriva dele — plano, execução, verificação.

Prompt-em-sequência (o padrão)

prompt 1  "faz login JWT"
    ↓
prompt 2  "ah, adiciona OAuth"
    ↓
prompt 3  "muda pra sessions"
    ↓
prompt 4  "rerroda os testes"

→  código inconsistente
→  sem rastro
→  contexto saturado
→  reverter = pesadelo

Spec-driven (GSD)

spec    contrato em .md no repo
    ↓
plan    tasks atômicas em XML
    ↓
code    1 task = 1 commit
    ↓
verify  testes contra a spec

→  contrato claro
→  commits rastreáveis
→  agente consulta spec
       qualquer hora
→  reverter = cirúrgico
Em PT
Spec = especificação. Um contrato em texto (markdown + XML) que descreve o que o sistema deve fazer, não como. Como está no disco, o agente não precisa lembrar — ele consulta. Por isso combate context rot.

GSD · GUILD AI11 / 23
Passos 01 a 03

O sistema escreve a spec antes de escrever o código

O GSD materializa o contexto em arquivos versionados:

  • DOCPROJECT.md · a visão, o porquê, stakeholders
  • DOCREQUIREMENTS.md · o que precisa existir pra "estar pronto"
  • DOCROADMAP.md · fases ordenadas por dependência
  • DOCPLAN.md · tasks atômicas em XML estruturado
Em PT
Por que XML? É um formato com etiquetas (<task>, <goal>) que o agente parseia com quase zero erro. Pense em formulário estruturado vs. texto livre.

Exemplo de task no PLAN.md:

<!-- lido pelo agente (Claude, Codex, etc) -->
<task id="1.2">
  <goal>health endpoint</goal>
  <files>
    src/server.py
    tests/test_health.py
  </files>
  <acceptance>
    GET /health → 200 {ok:true}
  </acceptance>
</task>

Cada tag vira uma promessa verificável — não dá pra fechar a task sem cumprir o <acceptance>.

GSD · GUILD AI12 / 23
Passo 04 // Execute

Waves — paralelismo com contexto fresco

Tasks independentes rodam ao mesmo tempo, cada uma num sub-agente próprio com 200k tokens limpos. Tasks dependentes esperam a wave anterior terminar.

Em PT
Sub-agente: outro agente rodando em paralelo com a memória zerada, dedicado a uma task só. O orquestrador é o agente principal que distribui as tasks e junta os resultados.
GSD · GUILD AI13 / 23
Passos 04 e 05

1 task = 1 commit · rastro limpo, reversão barata

Em vez de um PR gigante, o GSD emite um commit por task — cada um com mensagem padronizada e referenciando a task do PLAN.md.

Se algo quebra? git revert <sha>. Se alguém pergunta "por que isso existe?" — o commit aponta pra spec.

/gsd-verify-work roda os critérios de aceite — não deixa fechar uma fase sem UAT.

Em PT
git revert <sha>: desfaz UM commit específico sem perder os outros. Por isso o rastro atômico importa — você reverte cirurgicamente, não a noite inteira de trabalho.
$ git log --oneline
a3f2c1d task 1.3: config env vars
7b9e04a task 1.2: logger estruturado
e4d8f19 task 1.1: GET /health endpoint
c27ab03 plan: adiciona fase observabilidade
9f1d6e2 init: PROJECT.md + REQUIREMENTS.md

$ /gsd-verify-work
✓ task 1.1 · acceptance passou
✓ task 1.2 · acceptance passou
✓ task 1.3 · acceptance passou
→ fase pronta pra /gsd-ship

Autopiloto

Modo autônomo — /gsd-autonomous

Se o ROADMAP.md já existe e você confia no plano, esse comando executa todas as fases restantes do projeto em sequência, sozinho. Você vai fazer outra coisa.

Como funciona

  • LOOPPra cada fase pendente do ROADMAP
  • 01discuss — recolhe preferências da fase
  • 02plan — gera PLAN.md em XML
  • 03execute — roda tasks em waves
  • 04verify — valida UAT; se falha, para.

Quando usar · quando não

usa quando:
  ✓ ROADMAP confiável, fases independentes
  ✓ você já rodou GSD antes nesse projeto
  ✓ tem outra coisa pra fazer (almoço,
    reunião, dormir)

não usa quando:
  ✗ projeto novo, sem histórico
  ✗ fase com decisão gray-area (ele para
    e pede input — melhor decidir antes)
  ✗ você quer aprender o fluxo passo a passo
Em PT
Autônomo = roda sozinho, sem você precisar clicar a cada passo. Mas não é sem rede: ele para no primeiro teste que falhar e pede sua decisão — nunca fecha fase quebrada.
GSD · GUILD AI19 / 23
Pro caminho // boas práticas

Antes do GSD — pense bem. Muito bem.

O GSD é tão bom quanto a spec que você dá pra ele. Autonomous em cima de requisito mal-definido = 40 commits de lixo muito bem organizado.

Antipadrão

  • DONTPular o brainstorm pra "ganhar tempo" — você paga 10x em refactor
  • DONTRodar /gsd-autonomous cru — ele commita o que você pediu, não o que você quis
  • DONTTratar sintoma (código quebrando) quando a dor está na spec

Boa prática

  • DOBrainstorm amplo antes de /gsd-new-project — divergir, depois convergir
  • DOUse skills que forçam o pensar:
    Super-Powers · /brainstorm (Anthropic)
    Claude Octopus · /brainstorm · /prd (nyldn)
  • DOSe o GSD patinar ou reverter muito — pare. A spec está ruim, não o código.
Em PT
Brainstorm = fase de exploração, sem filtrar ideias. Super-Powers e Claude Octopus são pacotes open-source de skills que orquestram várias AIs em paralelo pra te ajudar a pensar antes de construir.

Pra levar pra casa

3 takeaways

01

Vibecoding falha em escala

Protótipo sim; código sério não. O gargalo é context rot + ausência de plano e verificação.

02

GSD troca cerimônia por sistema

Você descreve; o GSD planeja, executa em waves, commita atomicamente e verifica. Sem reuniões, sem template de PRD enterprise. E funciona em Claude Code, Codex, Gemini — não te prende a um fornecedor.

03

Comece com /gsd-fast hoje

Próxima task pequena sua (sem precisar de projeto GSD): instala, roda /gsd-fast, compara com o agente puro. Custa 5 min, gera intuição pro resto do fluxo.
